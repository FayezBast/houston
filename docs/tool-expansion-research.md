# Houston tool expansion

Checked September 13, 2026 against official documentation. Product priorities below are hypotheses, not measured demand. Existing Houston documentation already covers seven quota providers, Claude Code/Codex session hooks, Mac vitals, and read-only GitHub PRs/Actions; these are additions to that baseline.

## Product direction

Make the project the connecting unit: repository, local services, commands, agent sessions, deployments, and errors in one place. Start with a project hub, local ports/services, and user-defined commands; then add the integrations below. This is a product recommendation based on Houston's present surface and the integration capabilities, rather than a claim from the sources.

## Integration opportunities

1. **Docker: local service health and recovery.** Show running/stopped containers, published ports, and CPU/memory usage, with links to logs and explicit start/stop/restart actions. The official CLI already provides [container listings](https://docs.docker.com/reference/cli/docker/container/ls/), [resource statistics](https://docs.docker.com/reference/cli/docker/container/stats/), and [lifecycle events](https://docs.docker.com/reference/cli/docker/system/events/); the [Engine API](https://docs.docker.com/reference/api/engine/) is another transport. Start by invoking the installed CLI and respecting its selected context. On Mac, the default `/var/run/docker.sock` is optional; Docker Desktop also documents the user socket and context-based discovery. There is no SaaS OAuth step for local daemon access, but socket access is powerful and requires an available daemon and OS permission. Scope: list/health/ports first, on-demand logs next, selected-container actions afterward. [Mac permissions and socket behavior](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/).

2. **Vercel: the deployment result beside the repository.** Show building/ready/failed, branch, preview URL, and the latest failed build's logs. The API can [list deployments](https://vercel.com/docs/rest-api/deployments/list-deployments) filtered by project, branch, or commit, while [deployment events](https://vercel.com/docs/rest-api/deployments/get-deployment-events) provide build logs as JSON or a stream. Authenticate with a bearer access token; team resources need team context and rate limits apply. Scope: a selected project's latest deployments with click-through and meaningful transition alerts; do not start by implementing deployment creation. [REST authentication and team access](https://vercel.com/docs/rest-api).

3. **Sentry: production errors that need attention.** Surface newly observed high-priority unresolved issues, event/user counts, and a direct issue link, filtered to selected projects/environments. The [organization issues endpoint](https://docs.sentry.io/api/events/list-an-organizations-issues/) provides search, sorting, filtering, and issue metadata with bearer authentication; `event:read` is sufficient for this endpoint. [Issue details](https://docs.sentry.io/api/events/retrieve-an-issue/) provide additional stats and latest-event context. Scope: read-only issue summary and link-out, with deduplicated alerts. Keep full event payloads out of the default card; detailed event bodies are a separate data-access decision.

4. **Linear: a small assigned-work queue.** Show assigned issues, priority, status, and links; connect a chosen issue to the current project/task. Linear exposes its [GraphQL API](https://linear.app/developers/graphql), including the viewer and issue metadata, and supports [assignee filtering](https://linear.app/developers/filtering). Personal API keys suit an initial personal integration; a distributed product should use OAuth, as Linear recommends. The default OAuth `read` scope is enough for reading; mutations require their applicable scope, and refresh-token handling is required. Scope: assigned/in-progress issue cards and deep links first, status changes after the project workflow is clear. [OAuth scopes and authentication](https://linear.app/developers/oauth-2-0-authentication).

5. **More agent coverage: extend lifecycle hooks, then add opt-in MCP access.** Cursor is a concrete next adapter: its documented [hooks](https://cursor.com/docs/hooks) include `beforeSubmitPrompt`, `sessionStart`, `sessionEnd`, and `stop`, with completed/aborted/error status. Reuse Houston's existing local event bridge and store only the minimal session metadata. Broader extensibility can expose Houston state and user-approved commands through an MCP server, so compatible agents can ask about projects or invoke available operations. MCP's [server primitives](https://modelcontextprotocol.io/specification/2025-11-25/server/index) are tools, resources, and prompts; this does **not** establish a universal cross-vendor agent-session lifecycle. Lifecycle status still needs a supported provider hook or an explicit Houston reporting contract. Scope: one additional real adapter first; define a small event contract from working integrations before building a plugin marketplace.

## Positioning

[DevToys](https://devtoys.app/) already presents 30 offline developer tools, including JSON, Base64, JWT, diff, and regex tools. [Raycast's extension platform](https://developers.raycast.com/) provides native extension UI/API and distribution, while its [script commands](https://manual.raycast.com/script-commands) offer lightweight personal automation. These are useful reference points, not reasons to copy their breadth. Houston's proposed distinction is project-linked live state and timely actions in the notch. A utility pack can follow after that workflow earns daily use.
